# План создания GitHub Issues по спринтам для IDEAKIT MVP

## 1. Sprint 1 — фундамент системы

**Цель спринта:** два разработчика могут одинаково запустить и проверить приложение; PostgreSQL содержит утверждённую схему; базовые пользователи, каталог, интеграционные порты и надёжная фоновая обработка готовы для реализации пользовательских сценариев.


### `S1-01` — [Platform] Подготовить воспроизводимую среду PHP/Yii2

**Зависимости:** нет.

**Объём работы:**

- зафиксировать совместимые стабильные версии runtime;
- подготовить PHP-FPM, Nginx и Docker Compose для web- и console-процессов;
- подключить PostgreSQL, Redis и RabbitMQ;
- добавить безопасную типизированную конфигурацию окружения;
- предоставить единые команды запуска, остановки и диагностики через Makefile.

**Критерии приёмки:** чистое рабочее окружение запускается по README; web- и console-приложения проходят readiness-проверку; отсутствуют реальные секреты и зависимость от локальной конфигурации одного разработчика.

**Проверка:** запуск с чистого состояния, проверка web/console, соединений с PostgreSQL, Redis и RabbitMQ.

### `S1-02` — [Platform] Настроить обязательные проверки и CI

**Зависимости:** `S1-01`.

**Объём работы:**

- настроить проверку и исправление code style;
- создать единый test runner;
- настроить PHPStan для модулей и ядра;
- добавить архитектурные тесты зависимостей слоёв и модулей;
- включить обязательные проверки в GitHub Actions.

**Критерии приёмки:** одинаковые команды выполняются локально и в CI; нарушение стиля, тестов, PHPStan или архитектурных границ блокирует проверку; deployment не запускается из непредусмотренной ветки.

**Проверка:** успешный полный pipeline и контролируемое падение каждой обязательной проверки на тестовом нарушении.

### `S1-03` — [Platform] Создать миграции утверждённой схемы PostgreSQL

**Зависимости:** `S1-01`.

**Объём работы:**

- настроить namespaced migrations и тестовый контур PostgreSQL;
- создать утверждённые прикладные таблицы;
- добавить внешние ключи, уникальные и проверочные ограничения;
- добавить индексы под подтверждённые query paths;
- проверить применение и откат миграций на пустой базе.

**Критерии приёмки:** фактическая схема соответствует спецификации БД; семнадцатая прикладная таблица не создаётся; повторное развёртывание получает идентичную схему.

**Проверка:** автоматическая проверка миграций вверх/вниз, ограничений, индексов и состава таблиц.

### `S1-04` — [Platform] Реализовать надёжную фоновую обработку

**Зависимости:** `S1-01`, `S1-03`.

**Объём работы:**

- подключить Redis только через Infrastructure adapters;
- зафиксировать topology RabbitMQ;
- реализовать transactional outbox relay;
- подготовить runtime PHP workers, leases, retries и dead-letter обработку;
- реализовать scheduler и reconciliation зависших операций.

**Критерии приёмки:** бизнес-состояние остаётся в PostgreSQL; сообщение не теряется между транзакцией и RabbitMQ; повторная обработка идемпотентна; worker восстанавливается после прерывания.

**Проверка:** интеграционные тесты публикации outbox, повторной доставки, истечения lease и reconciliation.

### `S1-05` — [Users] Реализовать пользователей и административную аутентификацию

**Зависимости:** `S1-03`.

**Объём работы:**

- реализовать TelegramUser и TelegramBotSession;
- реализовать AdminUser, безопасные DTO и YiiIdentity;
- добавить пароль, административную сессию и завершение сессии;
- реализовать TOTP, recovery codes и роли;
- подготовить безопасный bootstrap минимум двух SUPER_ADMIN.

**Критерии приёмки:** Telegram ID уникален; BOT_BLOCKED восстанавливается после нового входящего update; административный доступ закрыт по умолчанию; роли и MFA проверяются сервером; секреты TOTP не попадают в логи.

**Проверка:** unit- и integration-тесты идентификации, сессий, MFA, recovery, RBAC и блокировки пользователя.

### `S1-06` — [IdeaCatalog] Реализовать доменную модель и хранение каталога

**Зависимости:** `S1-03`.

**Объём работы:**

- реализовать BusinessIdea и неизменяемую IdeaVersion;
- определить типизированные структуры карточки и отчёта;
- реализовать repositories и queries каталога;
- исключить ActiveRecord из публичных контрактов модуля;
- добавить optimistic locking изменяемых агрегатов.

**Критерии приёмки:** содержательное изменение создаёт новую версию; опубликованная версия не изменяется на месте; карточка формируется из проверенных структурированных полей.

**Проверка:** unit-тесты инвариантов и интеграционные тесты persistence и конкурентного обновления.

### `S1-07` — [IdeaCatalog] Реализовать версии и публикацию идей

**Зависимости:** `S1-06`.

**Объём работы:**

- реализовать lifecycle публикации;
- назначать неизменяемый возрастающий `sequence_no`;
- запретить перестановку опубликованных идей;
- реализовать снятие публикации с обязательной причиной;
- предоставить Application-контракты управления каталогом.

**Критерии приёмки:** публикуется только прошедшая проверки версия с готовым отчётом; снятая публикация исключается из новой выдачи; последовательность допускает пропуски, но не изменение порядка.

**Проверка:** тесты переходов статусов, конкурентной публикации, sequence и снятия публикации.

### `S1-08` — [Notifications] Подготовить внешние интеграции и уведомления

**Зависимости:** `S1-01`, `S1-04`.

**Объём работы:**

- создать общую основу HTTP-интеграций с таймаутами и безопасными ошибками;
- определить Application-контракты уведомлений;
- реализовать детерминированные fakes внешних сервисов;
- подготовить версионируемые шаблоны сообщений и асинхронный handler.

**Критерии приёмки:** доменные модули не зависят от конкретного канала; внешние вызовы заменяются fakes в тестах; повторная команда не создаёт дублирующее уведомление.

**Проверка:** contract-тесты adapters, таймаутов, ошибок и дедупликации.

### `S1-09` — [ContentGeneration] Зафиксировать контракты AI и структуры результатов

**Зависимости:** `S1-06`, `S1-08`.

**Объём работы:**

- определить provider-independent порты AI, embeddings, search и fetch;
- зафиксировать неизменяемые версии prompts;
- подготовить versioned JSON Schema кандидата, отчёта, claims и quality checks;
- определить allowlist данных, разрешённых для внешних провайдеров;
- реализовать строгую валидацию envelope и неизвестных версий.

**Критерии приёмки:** конкретный провайдер заменяется adapter-реализацией; невалидный или неизвестный результат отвергается; персональные данные не входят в provider request.

**Проверка:** schema/contract-тесты допустимых, неизвестных и повреждённых payload.

### Результат Sprint 1

Sprint 1 завершён, когда новый разработчик может поднять проект, применить миграции, выполнить полный CI-набор и через Application-контракты создать пользователя, версию идеи и публикацию, а также поставить надёжную фоновую команду без обращения модулей к чужим таблицам.

## 2. Sprint 2 — основной пользовательский сценарий

**Цель спринта:** пользователь проходит в Telegram полный путь от `/start` до просмотра карточки, деталей и отправки заявки; система надёжно фиксирует действия и умеет подготовить проверенный отчёт и PDF.

### `S2-01` — [IdeaFeed] Реализовать последовательную выдачу и доставку карточки

**Зависимости:** `S1-03`, `S1-07`.

**Объём работы:**

- выбирать минимальный доступный `sequence_no`, ещё не показанный пользователю;
- выполнять критический выбор под блокировкой пользователя;
- создавать durable IdeaDelivery до отправки;
- создавать IdeaImpression только после подтверждённой доставки;
- обработать `PENDING`, `SENDING`, `RETRY_SCHEDULED`, `DELIVERED`, `UNKNOWN` и `FAILED`.

**Критерии приёмки:** повторный callback не выдаёт вторую идею; одна версия не показывается пользователю повторно; постоянная ошибка доставки не создаёт показ; неопределённый результат не приводит к автоматическому дублю.

**Проверка:** конкурентные integration-тесты next, retries, unknown outcome и повторного callback.

### `S2-02` — [IdeaFeed] Реализовать действия и исчерпание каталога

**Зависимости:** `S2-01`.

**Объём работы:**

- фиксировать открытие деталей и запрос заявки;
- оставить старые карточки в истории с допустимыми действиями;
- запретить действия для снятой публикации;
- реализовать состояние исчерпанного каталога;
- формировать одно уведомление после появления новых публикаций.

**Критерии приёмки:** действия идемпотентны; снятая идея не выдаётся и не открывает новые детали; исчерпавший каталог пользователь получает не более одного уведомления на пополнение.

**Проверка:** сценарии повторных действий, снятой публикации и пополнения каталога.

### `S2-03` — [AgencyLeads] Реализовать жизненный цикл заявки

**Зависимости:** `S1-05`, `S1-06`, `S1-03`.

**Объём работы:**

- реализовать черновик комментария, согласие и подтверждение;
- создать статусы SUBMITTED, IN_REVIEW, QUALIFIED, UNQUALIFIED, CONTACTED, CLOSED и CANCELLED;
- сохранять историю переходов с сотрудником, временем и причиной;
- разрешить отзыв только до начала обработки;
- запретить второй активный лид пользователя по той же версии идеи.

**Критерии приёмки:** отмена до подтверждения не создаёт лид; повторная отправка возвращает существующий активный лид; новый лид возможен только после терминального статуса; недопустимый переход отклоняется.

**Проверка:** unit-тесты автомата статусов и конкурентные integration-тесты partial unique ограничения.

### `S2-04` — [AgencyLeads] Реализовать переписку и операторские контракты

**Зависимости:** `S2-03`, `S1-08`.

**Объём работы:**

- реализовать сообщения пользователя и оператора внутри конкретной заявки;
- предоставить queries списка и карточки заявки;
- предоставить commands изменения статуса и ответа оператора;
- ограничить доступ ролью AGENCY_OPERATOR;
- создать уведомление пользователю об ответе оператора.

**Критерии приёмки:** переписка не превращается в общий чат; сообщение связано с одним lead; VIEWER не видит комментарии и переписку; повторная команда не дублирует сообщение.

**Проверка:** authorization-, persistence- и notification-тесты.

### `S2-05` — [Telegram] Реализовать webhook, inbox и маршрутизацию updates

**Зависимости:** `S1-04`, `S1-05`, `S1-08`.

**Объём работы:**

- реализовать Telegram Bot API client;
- проверить webhook secret и ограничения входного payload;
- сохранять update в durable inbox с уникальным `(bot_id, update_id)`;
- быстро возвращать Telegram успешный HTTP-ответ после надёжной фиксации;
- реализовать Update DTO, dispatcher и подписанные callback-данные.

**Критерии приёмки:** повторный update не выполняет команду повторно; неизвестная команда или callback безопасно отклоняется; обработка выполняется worker без длительного webhook-запроса.

**Проверка:** contract-тесты Telegram, replay, повреждённой подписи, duplicate update и восстановления lease.

### `S2-06` — [Telegram] Реализовать `/start`, карточки и детали

**Зависимости:** `S2-01`, `S2-02`, `S2-05`.

**Объём работы:**

- реализовать короткое приветствие и немедленную первую карточку;
- реализовать «Следующая идея» и изменение клавиатуры старого сообщения;
- реализовать «Детали» для готового отчёта;
- детерминированно разделять длинный отчёт на несколько сообщений;
- показывать состояние исчерпанного каталога.

**Критерии приёмки:** карточка содержит название, проблему, аудиторию и монетизацию; итоговый текст карточки укладывается в согласованный объём; повторный callback не выдаёт две карточки; URL источников пользователю не показываются.

**Проверка:** интеграционный Telegram-сценарий `/start` → next → details → empty catalog.

### `S2-07` — [Telegram] Реализовать заявку, исходящие сообщения и BOT_BLOCKED

**Зависимости:** `S2-03`, `S2-04`, `S2-05`, `S1-08`.

**Объём работы:**

- реализовать ввод комментария, согласие, подтверждение и отмену;
- реализовать отзыв доступной заявки и ответ на сообщение оператора;
- реализовать outbound worker с пятью попытками и учётом `retry_after`;
- обрабатывать подтверждённую блокировку бота;
- восстанавливать ACTIVE после нового входящего update.

**Критерии приёмки:** лид создаётся только после подтверждения; пользователь видит текущий активный лид вместо дубля; инициативные сообщения BOT_BLOCKED не отправляются; ошибки доставки не меняют бизнес-статус заявки.

**Проверка:** полный сценарий заявки, временные и постоянные Telegram-ошибки, блокировка и разблокировка.

### `S2-08` — [ContentGeneration] Реализовать AIJob и конвейер генерации

**Зависимости:** `S1-04`, `S1-09`.

**Объём работы:**

- реализовать authoritative lifecycle AIJob и попыток;
- реализовать три попытки с утверждёнными задержками и jitter;
- обрабатывать волны по 10 кандидатов, не более 30 на пакет;
- реализовать нормализацию, классификацию, digital-fit и дедупликацию;
- сохранять версии prompt, schema, model config и validators.

**Критерии приёмки:** обработка останавливается после 10 прошедших проверку идей или 30 кандидатов; отрицательный/неопределённый digital-fit блокирует публикацию; после исчерпания попыток материал получает REVIEW_REQUIRED.

**Проверка:** unit-тесты pipeline и интеграционные тесты retries, лимита кандидатов, дедупликации и восстановления worker.

### `S2-09` — [ContentGeneration] Реализовать источники, quality gates и PDF

**Зависимости:** `S1-09`, `S2-08`, `S1-07`.

**Объём работы:**

- реализовать безопасный search/fetch pipeline;
- сохранять snapshots, provenance, регионы, claims и evidence;
- реализовать structural, source, numeric, freshness и region validators;
- добавить отдельный AI-critic без права отмены deterministic blocker;
- формировать и повторно использовать PDF для IdeaVersion.

**Критерии приёмки:** FACT и точные показатели имеют прямое допустимое доказательство; ERROR/UNKNOWN обязательной проверки блокирует публикацию; полное содержимое страницы удаляется в установленный срок; Telegram и PDF не содержат URL источников.

**Проверка:** тесты SSRF-защиты, fetch limits, numeric scanner, quality gates, revalidation и повторного использования PDF.

### Результат Sprint 2

Sprint 2 завершён, когда на тестовых интеграциях воспроизводимо проходит цепочка `/start` → карточка → следующая идея или детали → подтверждённая заявка → ответ оператора, а AI-конвейер создаёт структурированный проверенный отчёт и PDF без изменения бизнес-состояния внешним провайдером.

## 3. Sprint 3 — готовность MVP к запуску

**Цель спринта:** административные операции доступны через AdminPortal, подключены утверждённые реальные провайдеры, подготовлен стартовый каталог, staging и production проверены, а MVP прошёл финальную приёмку.


### `S3-01` — [AdminPortal] Реализовать вход и ролевой каркас

**Зависимости:** `S1-05`, `S1-02`.

**Объём работы:**

- создать Yii2-модуль AdminPortal;
- реализовать вход, TOTP, recovery и завершение сессии;
- ограничить разделы и действия ролями SUPER_ADMIN, CONTENT_MANAGER, AGENCY_OPERATOR и VIEWER;
- добавить защиту сессии, CSRF и безопасные ошибки;
- реализовать единый audit hook для критических административных действий.

**Критерии приёмки:** неаутентифицированный доступ закрыт; каждая роль видит только разрешённые разделы; критическое действие требует подтверждения и причины; повторный TOTP для каждого действия не запрашивается.

**Проверка:** feature-тесты входа, MFA, recovery, logout, CSRF и матрицы ролей.

### `S3-02` — [AdminPortal] Реализовать управление каталогом и генерацией

**Зависимости:** `S1-07`, `S2-08`, `S2-09`, `S3-01`.

**Объём работы:**

- реализовать список и карточку бизнес-идеи;
- реализовать просмотр версии, отчёта, claims, sources и quality checks;
- реализовать создание исправленной версии;
- реализовать публикацию и снятие с обязательной причиной;
- реализовать экран AI-заданий и ручной повтор.

**Критерии приёмки:** CONTENT_MANAGER выполняет полный content workflow без прямого доступа к БД; опубликованная версия неизменяема; блокирующий quality check нельзя обойти интерфейсом; конфликт `lock_version` отображается безопасно.

**Проверка:** feature-тесты content workflow, авторизации, подтверждения действий и конкурентного изменения.

### `S3-03` — [AdminPortal] Реализовать заявки, пользователей и аналитику

**Зависимости:** `S2-04`, `S3-01`.

**Объём работы:**

- реализовать очередь и карточку заявок;
- реализовать допустимые переходы статусов и переписку оператора;
- реализовать просмотр пользователей и BOT_BLOCKED;
- реализовать управление администраторами и сброс MFA другим SUPER_ADMIN;
- вывести базовую агрегированную продуктовую аналитику.

**Критерии приёмки:** оператор работает без доступа к БД; VIEWER не видит персональные комментарии и переписку; каждый переход статуса и критическое действие аудируются; аналитика не раскрывает персональные данные.

**Проверка:** role-based feature-тесты заявок, переписки, пользователей, администраторов и агрегатов.

### `S3-04` — [AdminPortal] Провести сквозную приёмку административного интерфейса

**Зависимости:** `S3-01`, `S3-02`, `S3-03`.

**Объём работы:**

- пройти ежедневные сценарии всех четырёх ролей;
- проверить запрещённые прямые URL и изменение чужих данных;
- проверить ошибки, пустые состояния и optimistic conflicts;
- подтвердить отсутствие необходимости ручного редактирования БД;
- исправить найденные блокирующие дефекты в пределах Issue либо оформить отдельные `bug`.

**Критерии приёмки:** все обязательные административные сценарии выполняются через UI; отсутствуют открытые Urgent/High дефекты AdminPortal; проверка проведена вторым разработчиком.

**Проверка:** подписанная матрица ролевых сценариев и успешный автоматический feature-набор.

### `S3-05` — [ContentGeneration] Подключить реальные внешние провайдеры

**Зависимости:** `S1-09`, `S2-08`, `S2-09`, готовые тестовые credentials вне репозитория.

**Критерии приёмки:** смена provider config не затрагивает Domain/Application; автоматического failover нет; персональные данные не передаются AI; provider errors классифицируются и безопасно повторяются.

**Проверка:** contract-тесты adapters и контролируемые staging-сценарии success, timeout, rate limit и malformed response.

### `S3-06` — [ContentGeneration] Подготовить и опубликовать стартовый каталог
