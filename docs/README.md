## Документация проекта «IDEAFLOW»

Данная папка содержит всю техническую и проектную документацию.  
Она организована так, чтобы упростить навигацию, поддержку актуальности и совместную работу.

---

### Структура папки `docs/`

```
docs/
├── README.md       # Этот файл - описание процесса документирования и навигация
├── contributing.md # Правила работы с репозиторием (Git, PR, CI)
├── specification/  # Всё, что связано с планированием и требованиями
│ ├── README.md     # Ссылки на все спецификации
│ ├── mvp.md        # Описание MVP (кратко, цели, сценарии)
│ ├── technical-spec.md # Техническое задание (архитектура, стек, API)
│ ├── planning/     # (опционально) планы, дорожные карты, оценки
│ └── resources.md  # Полезные ссылки, исследования, референсы
├── core/           # Документация по ядру (Core)
│ ├── README.md     # Общее описание ядра, его слоёв и модулей
│ ├── architecture.md # Детали чистой архитектуры, DDD, CQRS
│ ├── domain/       # Описание доменных сущностей, агрегатов, сервисов
│ ├── application/  # CQRS команды/запросы, хендлеры
│ ├── infrastructure/ # Реализации репозиториев, клиентов, кэша
│ └── api/          # Спецификация внутренних и внешних API (если применимо)
├── modules/        # Документация по отдельным модулям (Telegram‑бот, админка и т.д.)
│ ├── telegram-bot/ # Всё о боте: компоненты, сессии, webhook
│ │ ├── README.md
│ │ └── ...         # Структура папки модуля - произвольна

│ ├── admin-portal/ # Веб‑интерфейс для администратора

│ └── ...           # Другие модули по мере появления
├── .images/        # Графические файлы (скриншоты, схемы в PNG/SVG)
│ └── (хранятся изображения, на которые ссылаются из markdown-файлов)

└── (файлы .puml, .mmd и т.п., из которых генерируются изображения)
```

### Как работать с этой документацией

1. **Язык** - русский (для внутренней документации) или английский (если предполагается открытый исходный код). Для данного проекта предпочтительно **русский**.
2. **Формат** - все файлы пишутся в **Markdown** (`.md`).
3. **Ссылки** - используйте относительные пути внутри репозитория. Например: `./specification/mvp.md`.
4. **Диаграммы** - храните исходники в `.diagrams/`, а сгенерированные изображения (PNG/SVG) - в `.images/`. В Markdown вставляйте ссылки на изображения из `.images/`.
5. **Каждый модуль** - в папке `modules/<module>/` должен быть как минимум файл `README.md` с описанием назначения, интерфейсов, зависимостей и способа запуска.
6. **Актуальность** - при изменении кода или архитектуры обновляйте соответствующую документацию в рамках той же задачи (Pull Request).
7. **Версионирование** - документация версионируется вместе с кодом; для крупных изменений указывайте дату и автора в начале файла (опционально).

---

- **Новичкам** - начните с `./specification/mvp.md` и `./core/architecture.md`, чтобы понять суть проекта и его устройство.
- **Разработчикам** - при добавлении новой функциональности создавайте или дополняйте файлы в `core/` и `modules/`.
- **Администраторам** - инструкции по развёртыванию и настройке выносятся в отдельные файлы внутри `core/infrastructure/` или в корневой `README.md` проекта.

### Рекомендации по именованию файлов

- Используйте **строчные буквы** и **дефисы** вместо пробелов: `technical-spec.md`, `mvp.md`.
- Для изображений - осмысленные имена: `architecture-overview.png`, `erd.png`.

---

### Генерация диаграмм

Пример использования PlantUML:

1. Поместите код в `.diagrams/context.puml`.
2. Сгенерируйте PNG, например, с помощью локального PlantUML или онлайн‑сервиса.
3. Сохраните результат в `.images/context.png`.
4. Вставьте в документ: `![Контекст](./.images/context.png)`.
